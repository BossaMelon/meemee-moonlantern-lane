日期：2026-10-26。设计基线：main `ab548ab7aff8d4d0f2fb0b56c3a3cc8807f08a9c`。这是待实现、待审阅的下一阶段规格，不是新游戏已完成声明。旧 [三日契约](05-restaurant-prototype.md)、[自动验收](../contracts/prototype-v1.json) 和已合 PR #9 保留；进度/证据只进入 [项目状态](project-status.md)，任务权限只由 [任务清单](../harness/tasks.json) 声明。本次 H02 交付仅此文档，实施须经总协调安排的新范围主审与派发。

## 1. 目标与完成边界

用户已明确反馈“不好玩、地图和战斗单调”。本阶段要验证：玩家为今晚菜单选取材路线，在战斗中改变做法，回店兑现收获，并因一个具体的新打法而愿意主动再开一晚。Steam 可售品质是长期目标，本切片通过不等于商品、平台或发行验收完成。

一晚以 **10–15 分钟、探险 3–5 分钟** 为观察目标；熟练玩家更快不判失败，不添加等待、挂机进度、签到或退出惩罚凑时长。只做一张紧凑、两路相通的菇圃、五道既有菜、三波营业、一种新敌人。第二晚复用地图和规则，仅变需求组合/资源配置，允许实际再玩并验证首晚成长；不扩七日、大世界、技能树、反弹或护送。

阶段完成分开判断：

1. **可交付试玩**：本规格的新行为有真实执行、自动正反例及三种输入运行证据；新旧 profile 隔离，旧技术回归仍通过，可打开/暂停/保存/退出恢复。
2. **体验判断**：用户或咩咩实际试玩，记录第 7 节假设是否成立。无人试玩标“体验待验”；已观察到单调则明确该假设失败，先修机制。首轮不以招募五人为开发门槛，不外发邀请。
3. **扩充决定**：总协调基于实际体验决定修订或继续。自动断言数、资产数、时长和礼貌认可均不能替代这个决定。

当前保留私人 HP 题材、人物与原创像素表现，内容权利/原创商业路线待用户决定，不先改主题。Steam 官方规则要求具有内容所需权利；此处只记录发行待决条件，不认定已有商业授权，也不发起付费或上架。[Steamworks onboarding](https://partner.steamgames.com/doc/gettingstarted/onboarding)

## 2. 一晚的可玩闭环

| 环节 | 实际选择与反馈 |
|---|---|
| 出发前 | 看今晚三波需求摘要与两条取材路，采购基础料；可批量做一份餐前料理，自食或留售二选一。未食用也能完成。 |
| 菇圃 | 学会一次引冲撞桩；在棚架与湿渠之间行走取舍，可经中段连接处换路。材料够用可以返店，也可深入争取月心菇。 |
| 备餐 | 根据真实收获与需求，选普通饼/汤/炖锅或两种稀有料变体；设菜单与明确的供应优先序。数量、成本和留下的材料始终可见。 |
| 营业 | 普通出餐自动进行，分三短波；波间停时，可补备餐、换菜单、调整优先序再主动开下一波。经营结果指出未匹配、未备足、供餐拥堵或预算原因。 |
| 收工 | 展示现金、菜品毛利、设备/升级支出、剩余料与错失的需求；用实际菜品收入购买散射杖；点击进入次晨立即解锁、装备并重新出发，用新打法选路，不插入现实等待。 |

时间花在观察、走位、取材和选择上。每波已处理完即结束，不能用固定最短播放时间拖住玩家；全部结束可立即收工。成长试用沿合法 next_day→装备→探险，不新增练习模式，不在当晚重置探险次数。

## 3. 地图、敌人与两条打法

逻辑空间先沿用 960×540，无新相机系统。E01 的地图数据是碰撞/水区/出生点/资源点事实源；A01 按同一坐标画可读地形，不能画出实际上可穿透的实墙。边缘细节收敛，关键预警不被纹理、前景或 UI 遮挡。E01消费既定 manifest ID：`garden_stump`（含 footprint/pivot）、`sporecaster_idle/windup/release`、`spore_cloud`、`water_ripple`；敌人 kind 固定为 `sporecaster`。A01仅追加这些必要表现到小 atlas，旧资产字节保留，不先画完整地图拓扑。

| 区域 | 规则与回报 |
|---|---|
| 共用入口 | 一只冲刺怪与可绕行菇桩，安全地演示“锁定方向→躲开→撞桩硬直”。入口不是必须清场才能离开的门锁。 |
| 上层棚架 | 干路较短，实体菇桩遮挡弹体并切断直线冲刺；材料少但路径明确。适合直线杖拆后排、引怪撞桩、迅速取足返店。 |
| 下层湿渠 | 开阔水区与转角，星火菇资源较集中；步行穿水会更慢，投手的孢子区封住安全站位。适合风咒清场、推退和散射覆盖，再集中收获。 |
| 相通深处 | 两路均能到达，盾精英与投手组成可选挑战；击败精英取得 moonheart。先拆投手或制造精英破绽由玩家决定，不按固定第 3 日才允许进入。 |

最小地图只有三个遭遇：入口教学、岔路中的冲刺/投手组合、深处精英/投手组合。有限敌人和资源，不刷怪、不强制清图；资源点位置、敌人身份和掉落在本次出发时确定。第二晚只从有限已验配置中变化，提前显示主要资源/需求，不靠随机稀缺锁基础经营。

**地形规则：**菇桩为静态实心碰撞体，阻挡玩家、敌人和双方弹体，不做反弹/破坏。玩家闪避撞桩会停止，不穿墙；冲刺怪/精英高速撞桩停止本次攻击、进入硬直，精英同时暴露护盾。以扫掠碰撞处理高速运动，同一冲刺只触发一次硬直，不能贴桩无限刷新。湿渠只减速步行，双方一致，初值倍率 0.65；闪避/冲刺不叠加水减速，弹体不受水影响，水本身不掉血。

**敌人规则：**保留冲刺怪与正面盾精英的预警/破绽，新增 `sporecaster`：有射线遮挡检查，向玩家当时位置投掷孢子，落点先预警再形成短时危险区；不持续追踪落点。孢子区对玩家造成一次接触伤害并减速，普通敌人在区内也减速；同区停留不每帧伤害，不因重新进区重复结算伤害。多个减速取最小倍率，不相乘。投手击败掉 `sparkcap`，不新增食材 SKU。

**先只做两项环境协同：**引冲撞桩产生可攻击的硬直；`gust` 清除范围内已形成的孢子区并推退敌人。风咒不反射弹体、不取消已飞出的孢子弹或精英环形波；清除事件列出 hazard ID，视觉立即同步。推退撞桩仅停止，不额外套冲刺硬直。普通敌人的孢子减速、菇桩遮挡和精英在前/投手在后让目标顺序产生区别。

计时待模拟初值：撞桩硬直 1.2s；孢子落点预警 0.8s、区半径 45、存续 3s，单区单次伤害 1；投手最短投掷间隔 2.5s。保留可读反应窗口，不以加血/伤害替代组合。取消新 profile 的 180s 强制返程，保留经过时间统计；生命归零/主动撤退仍保留已收集物、无债务、不清档，未拾取物离场明确放弃。

## 4. 五道菜、波次与成长

沿用 `floating_pie/ember_soup/moon_stew/star_soup/comet_pie`、四种基础食材及 `sparkcap/moonheart`。配方投入和默认批量能力不变；新 profile 从第一晚就稳定供应暖焰草，`supply_pass` 不再作为前置，不改旧 profile 的解锁规则。保留开店遗留锅留用或售回 18、替代品 30 的机会成本；有锅才可制作炖锅。

**核心阶段边界：**`shopping → preparation → trading(波1) → intermission → trading(波2) → intermission → trading(波3) → closing → settled`。intermission 是核心持久化 phase，不是把 trading 的 paused 置 true。仅当本波全部顾客已成交/离开且 reservations 为空才进入波间；第三波直接 closing。craft 仅 shopping（餐前）/preparation/intermission 可用，display/undisplay/price/set_menu_priority 仅 preparation/intermission 可用，buy 仍仅 shopping，装卸锅仅 preparation。active trading 即使 UI 暂停也拒绝制作和移菜单；解除暂停不能自动开始下一波。每次 start_wave 原子提交目标 wave_id、复用已生成队列，不再抽客或刷新预算。波尾清零经营累积余帧，剩余 delta 不流入下一波；换波不得调用 _begin_day、刷新每日次数/供应或重置 RNG。intermission 的经济写操作白名单仅 craft/display/undisplay/price/set_menu_priority/start_wave；其他指令沿明确阶段 guard，暂停/保存仍可用。

**三波客流**采用“赶路客较多→巡护正餐→雨中返程”的可读摘要，数量和需求分布在采购前给出；实际队列与预算在开夜时由固定种子生成并保存。首晚 day=1，独立 night.weather=rain、night.event_id=rain_return，需求与天气加价读取这些字段而非伪装 day=3；首晚天气/活动、预报、三波队列均进 snapshot。普通客不需要逐个收银；海格仍是可跳过、停时的短委托，不锁第二晚。稀有菜的照路/庆功需求可预见，缺稀有材料仍能完成当晚。不要把三波做成旧每秒成交循环乘三。

供应有真实在途份数和有限通道；两路线的操作区别如下：

| 路线 | 备餐与实际出餐规则 | 成本与取舍 |
|---|---|---|
| 浮空小食 | 本波新制的浮空饼/彗星饼可同时有两份飞向外带客，发出后不能改售给另一人；玩家以小批量、波间补做维持浮空周转。 | 较少准备资金、较多波间决策；跨波剩饼仍能吃/卖，但浮空加速结束，按普通单通道交付，不销毁或降原价。 |
| 热锅正餐 | 装配坩埚后，一次可从已备炖锅中预留最多三份给当前正餐组，完成后同时交付；锅内最多三份保温库存可跨波保留，无需重做。 | 保留厨具、提前占用材料与菜单位；换取跨波供给余量，不能凭空补满锅。 |

**保温是核心状态：**新制炖锅实例为 hot；本波结束且所有在途交付已完成时，已安装锅按菜单优先、UID升序自动将最多三份仍为 hot/held 的剩余炖锅标 held（cooled 不可重新保温），写入 service.held_uids。这些份数下一波仍满足暖身订单的温度条件，可直接出锅；其余跨波炖锅转 cooled，仍可作 hearty 正餐出售/保留，但不再满足暖身订单的额外温度条件，不销毁、不降原价。菜品 intrinsic_tags/effect_id 是制作时的固有效果，拆锅不会删除 warming/heat_hold/self_stir 等；temperature 与浮空本波资格是独立动态状态，不能改写 catalog 标签或以全局厨具状态替代实例判断。未上菜单的储藏炖锅不自动占保温位。移出保温锅/拆卸或出售锅会将对应 held 转 cooled，不可靠再次 display 或读档重新变热；next_day 保留真实温度/库存，旧 prepared_wave_id 不伪装新制。UI明确显示热、保温、已凉及锅内余量；变化由波边界/合法物品操作触发，不按现实离线时间发生。

汤类按普通通道交付；其固有 `warming/heat_hold/trail_light` 决定匹配（两种汤不新增温度衰减），未装锅不能获得锅的成组交付。所有批量交付仍逐份核算食材成本、顾客预算和交易身份。普通/浮空/锅批次的交付初值分别 3s/1.5s/4.5s；普通通道最多一单，浮空通道两单，锅批次每次最多三单。三通道可并行，但只能使用已上菜单的真实份数。每位普通客有可见、可暂停的宽松等候窗口，初值 20s；全部成交或明确离开即结束本波，无最低波长、无额外罚款。首晚普通客初值为波1八位（5 quick、3 warming+heat_hold）、波2九位（3 quick、6 hearty）、波3九位（5 quick、4 warming+heat_hold）；均需 meal，同波全部在开波时到达，预算在23–30中按种子产生，队列按上列需求顺序编号（如波1 c01–c05 quick、c06–c08暖身），同类预算按此序列取随机值。采购预报公开数量/需求与预算区间。稀有需求用第二晚已验配置替换少量普通需求，不叠加首晚人数；海格委托另计并冻结整个波钟。调度每个固定步按到达序/订单ID扫描，按菜单优先序选可匹配且通道空闲的具体UID；跳过暂不可服务订单，不阻塞后续合法订单。等待满20s未预留就离开，记录拥堵/缺货/预算原因；同tick先完成已发交付，再处理到期，再为未到期订单预留，开波时可立即预留。波1的直接反例：同为60起始现金、花43制作5饼+3汤，所有客人预算≥23且标准价可付；若5饼是跨波余货，八单共用普通通道，在t=0/3/6/9/12/15/18接走前七单，c08在20s离开；若本波新制，饼走浮空、汤走普通，t=9前八单全部交付，实际挽回c08的暖焰汤收入。差异来自实例的新制资格及供餐拥堵，不是多给材料或顾客预算。跨波保温的反例：同样四份剩余炖锅面对下一波四名暖身客，锅保留的三个UID可在4.5s同时交付，第4份cooled不能冒充热菜；未装锅跨波则四份均cooled、暖身成交为0（仍可卖给hearty客）。快餐与保温均须在真实账本出现成交差异，不能只缩短动画或改标签。实际长度和拥堵是否有趣须试玩，不能靠延长秒数解决无决策的问题。

发出时将菜单 UID 移至 reserved，仍计入总库存与容量，交付时原子扣库存并收款；取消/结束前没有已提交交易就不能收钱。预留单不再次参与匹配，保存恢复不重发；同客至多成交一次。已发出订单的等候计时停止，避免菜在途中被无故丢弃。波间才允许补制作/换菜单，菜单排序决定多个合法菜的优先级，不能由 catalog 枚举顺序替玩家决定。匹配温度/效果/价格所选的 item_uid 必须就是预留和最终扣除的同一实例，不能先按SKU匹配再任取一份；同菜按UID升序。菜品实例记录 prepared_wave_id：开店前制作归首波，波间制作归下一波，跨夜仍可卖但不重新获得浮空加速。日结报表将备料、未售、在途、成交区分清楚。

**材料四用：**正常拾取后可直接售回、加工后出售、加工自食或跨夜保留。新 profile 中 `sparkcap/moonheart` 的固定售回初值为 4/8；复用 recycle，仅 shopping/preparation、bag 中足量的真实UID可售回；未知ID、超量、装配/菜单/预留中物品原子拒绝。原料不能 display/price 或响应顾客订单，不能从供应商购入这两种稀有料，来源/掉落身份仍受限。免费取得成本为 0，原料售款与菜品毛利分列；制作的机会成本可提示原料售回价，但不能重复计入现金账。存档、跨波、跨夜不额外生成材料或售价。

**餐前效果只两种，同次只一种：**食用 `floating_pie` 得 `light_step`（下一次正式探险的首次闪避延长至 300ms，速度不变）；食用 `star_soup` 得 `clear_breath`（下一次首次风咒范围由 120 扩至 160，推退距离不变）。实际消耗一份储藏菜、不获售价，待用槽保存 effect_id 与来源 item_uid；同菜按UID升序选择，消费请求防重，不能消耗菜单或预留实例；已有待用效果再吃原子拒绝，提示先保留。开始正式探险成功时原子清空待用槽并转移到动作状态，创建失败保留原槽；首次对应动作消耗；离场未用不返还，暂停/读档不刷新。允许采购阶段在灶台做餐前料理，仍扣真实食材；两种都不设为出发门槛。

**首晚就接触成长：**新 profile 起始有基础杖、闪避、风咒，使首段即可学习两项协同；`field_kit` 改为购买散射杖，与厨房第三菜单 `shelf` 争用经营预算，不再次日一次送杖和技能。只在日结购买，仍要求累计真实菜品销售收入达门槛；购买记 pending_unlock，合法 next_day 在次晨激活，玩家立即装备并进入下一次正式探险，无现实等待。保留每日正式次数约束，不为当晚试招假刷新日期/次数，不新增 practice mode。

新 profile 的两项升级价格暂以各 60、菜品收入门槛 24 为模拟初值，不是已平衡结论。两条正常路线都必须在首晚能买到至少一个打法选择，买后还能正常补基础料；若两项随意买齐且不影响任何后续选择，或常规购买迫使应急恢复，则调数值并复验。现金、毛利、升级投入、剩余库存和用时分开比较，不能用期末现金单指标宣称路线优劣。

## 7. 人类可观察假设与停止扩充条件

先请用户或咩咩按自己的方式玩一晚，不提示应该喜欢哪条路线或必须续玩。可记录屏内行为、停顿与原话；自动代理轨迹仅说明可达性。小样本用于找到失败，不宣称统计证明或“上瘾”。

| 假设 | 观察与失败判据 |
|---|---|
| 地图选择有理由 | 玩家能因菜单/装备/风险说明选路，并至少一次利用连接处或提前撤回；若只按颜色随便选，或两路没有任何行为差别，地图假设失败。 |
| 怪物组合改变做法 | 遇到投手+冲刺/盾怪后，玩家主动改目标顺序、引撞桩或清孢子；若持续后退射击即可无差别包办，先修遭遇，不加房间。 |
| 料理路线有不同节奏 | 玩家能感知小批浮空补餐与锅餐跨波余量，并用实际剩料调整一次菜单；若仍只是照清单点完等金币，两环连接失败。 |
| 成长产生可指认期待 | 试散射杖后，玩家说得出想重试哪处、为什么；若只知道“更高级”，装备价值未建立。 |
| 自主再玩一晚 | 明确可以结束后，记录是否主动继续及具体计划；若用户仍反馈单调/无期待，趣味不合格，保持待改，不以旧技术绿灯宣布目标完成。 |

没有人类试玩时，只交付“可试玩、机械验证通过”的候选。反馈失败时修最薄弱的一环，再作有针对性的试玩；不自动扩大菜谱、夜数或素材规模，也不据一人一次通过宣称 Steam 可售品质已完成。
