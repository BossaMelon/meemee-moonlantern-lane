# 开发接手说明

更新：2026-10-25。先读 [仓库约定](../AGENTS.md)、[项目状态](project-status.md)、[技术决定](04-technical-decisions.md) 和 [任务清单](../harness/tasks.json)。当前事实以实际文件、工具输出和证据为准。

## 1. 当前授权与历史

用户已授权持续推进实现，所有代码、内容、素材整合、场景配置与测试由用户可见的独立 chat 完成，禁止 sub-agent。仅总协调 chat 创建和派发实施 chat；总负责人负责收敛、协调、验收和合并，不编写实现。按任务指定模型与推理强度，全部 Standard（`service_tier=default`），禁止 Fast/Ultrafast；不改全局设置。harness 前置已验收，当前推进三日原型。

历史上本目录仅有研究、设计与接手文档，并非 Git 仓库；那一轮仅交付文档，建议桌面浏览器优先。现在已建立 public GitHub 源码仓库，明确最终 Windows/iOS、触屏/手柄，选择 Godot。历史评审与原始设计初值保留在 [review-notes](review-notes.md) 和 [设计探索](02-game-design.md)；不要沿用已过时的“仅交付文档”或“平台待确认”作为停止实现的理由。

这是送给网名咩咩的老婆的作品。经营是主体，用户最新确认以《哈利波特》为背景的魔法料理饭店，熟悉角色指 HP 人物。《潜水员戴夫》不是《植物大战僵尸》。研究里的玩家意见不等于留存因果；“好玩”和“上头”尚未验证。

## 2. 接手检查与协作

检查实际 host、适用指令、工具版本、分支、工作树、未提交变更和任务所有权。共享 checkout 保持 `main`；有修改必须在 native 工具创建或复用的隔离工作树、独立分支上完成并开真实 PR。只修改任务允许路径，保留其他人的修改和恢复点。

依赖以任务清单为准。H02/H03 先做各自范围检查并由负责人审阅合并，H01 最后做完整 harness gate。三项全部验收合并后才可开始 P01 核心；P01 发布实际接口后才可开始 P02 UI。不要让 UI 猜核心函数，也不要提前制作完整世界或批量素材。

## 3. 已选技术边界

采用 Godot 4.7.2 标准版 + GDScript，原创 2D 像素小店、固定三分之四斜俯视，Compatibility 渲染器。通过绘图构建可信魔法世界；保留可复用巷口与街景，内部转为厨房、用餐区和上菜柜台。沿用通用核心与布局，像素美术由 A01 制作，UI 消费资源。HP 人物采用新绘制的原创像素表现，不搬电影截图；不继续旧文具商品图标。先在当前 Mac 上验收可运行原型；最终交付方向是 Windows 与 iOS。触屏与手柄操作从原型纳入，实体手柄、Windows 和 iOS 的实际验收分别记录。

- `game/core/`：无场景和渲染依赖的 `RefCounted` 逻辑，处理库存、现金、交易、阶段、需求、升级、内容校验与种子随机。
- `game/ui/`、`scenes/`：呈现、焦点导航、触屏/鼠标/手柄输入、暂停反馈和声音；P02 可维护 `assets/SOURCES.md`，A01 独占 `assets/pixel/**`，路径权限以任务清单为准。
- 存档：有版本号的 JSON，使用 Godot `user://`；保存完整玩法状态及随机种子/内部状态。恢复不能靠重新抽货获利。
- `project.godot` 归 P01，以便实际 headless 运行；可预先声明未来主场景，但 P02 场景尚未合并时不宣称游戏可玩。首个游戏 PR 的 prototype CI job 由工具 owner 在同一 PR 串行启用，避免多人同时修改 workflow。
- `tests/core/`、`tests/run.gd`：核心与契约 runner；`tests/runtime/`：运行检查。具体公开 API 由 P01 实现并交接。

交易必须防重复扣款、发货和结算。NPC 动画、渲染帧率和窗口切换不能改变经济结果。暂停时营业时间停止；每个阶段的可返回范围和提交点须明确。存档覆盖阶段与时钟、待处理顾客/订单、库存实例、现金、升级、已读事件及随机状态；损坏或不兼容存档不能静默重置覆盖唯一有效存档。

## 4. 首个交付与后续边界

首个交付为可连续经营三日的魔法料理饭店：采购、备料、魔法烹饪、出餐、结算、升级、次日、暂停与存档恢复。已知菜谱默认批量制作；保留通用库存、账本、批量加工、订单状态机、存档和输入成果，停止旧奇物杂货/文具家居内容扩充。

H02 由可见聊天 `01a172cf-4b61-7862-84fb-8fc3f779723f` 在 `docs/05-restaurant-prototype.md` 冻结最小设计并更新 contracts/fixtures。冻结前，实施 chat 不自行发散菜谱或修改核心契约。快餐小食与热食炖锅等路线须有实际行为差异；厨房奇物设备有留用/出售机会成本；雨天预告须带来可提前准备的暖身/保温需求。自动搅拌、持续保温、漂浮料理等魔法须改变烹饪与菜品行为，不能仅改 UI 词。

轻动作采集必须是实际可玩的短探险：一小场地、约 2–3 分钟、1–2 种食材怪，移动/施法/闪避、真实位置、敌人预警和击败掉落；不以菜单 roll 或一键胜利冒充。基础食材稳定供应，战斗食材解锁或改变可选魔法料理，失败无负债/不清档，可暂停保存。料理可出售或自己吃，先一种小能力影响下一次探险；探险、菜单/特殊客人、厨房收入、下一次探险须互相供给。

H02 还须冻结动作操作/API 与可执行验收：确定性、掉落防重、暂停恢复，以及键鼠/触屏/手柄对移动/施法/闪避的映射。动作实现 chat 和与 UI 互斥的路径由总协调稍后指定，其他 chat 不抢写；不增加大地图或战斗系统堆料。

熟客先做一位的偶发可选短委托，优先海格巡护带餐、两种料理解法；细则由 H02 冻结，不新增大地图或长剧情。旧 catalog 的测试绿仅证明旧候选与通用底座，不能作为新饭店产品完成证据。

先解决循环问题。没有真实人类试玩时，只能记录技术验收，不宣称好玩，不自动扩充七日内容。得到试玩反馈后再决定节奏、更多熟客与后四日内容；当前已授权 A01 制作原型像素美术，不把素材数量作为早期进度。

## 5. 验证与失败诊断

自动验收源为 [原型契约](../contracts/prototype-v1.json)，场景输入为 [夹具](../tests/fixtures/prototype-scenarios.json)。统一入口：

```sh
python3 tools/gate.py --stage harness
python3 tools/gate.py --stage prototype --godot /absolute/path/to/Godot --report output/prototype-gate.json
```

prototype 实际调用 Godot 的 `tests/run.gd` 并传入绝对报告路径；协议见 [技术决定](04-technical-decisions.md)。不能以空 runner、少用例、跳过必需检查或手写通过报告替代验证。

重点检查库存/现金守恒、重复结算、零资金恢复、稳定基础供货、价格/预算边界、批量加工、存档/随机状态一致性。料理契约冻结后，用同组固定种子比较两条料理路线、设备留用与雨天备货，查看现金、库存、升级、恢复次数和失败原因；模拟分数不能解释成人类快乐。

实际运行覆盖一日至三日关键路径，暂停、保存退出重启和需求备货。截图检查实际探险中的位置/敌人预警/掉落、采购、备料、烹饪、出餐、熟客委托、雨天需求、结算和较窄横屏：文字遮挡、物品可辨认、点击目标大小、焦点可见、暂停反馈。自动生成截图后还必须查看截图。

失败记录候选/base SHA、复现命令、预期/实际、首个具体错误、日志或截图、owner、下一步。定位原因并定向修复，不删除失败用例或降低契约来获得通过。

## 6. 评审与交付

非平凡候选由总协调安排一次独立只读 reviewer，评审也不得通过 sub-agent 执行；提供需求和实际 diff/快照、候选 SHA 与证据。总负责人检查实际产物和有证据的发现；修复后定向验证，不因新 SHA 反复完整重审。最多一次有具体范围理由的复审，服从用户评审预算。

PR 完成并不等于验收通过。总负责人在 gate、评审和实际运行证据满足后合并；基线变化只刷新失效证据。维护唯一的项目状态文件，区分代码、实际运行、自动化、人类试玩、平台适配与发布。

无需为已授权的可逆细节重复询问用户。购买、付费服务、外部发布或部署保持未授权；需要时先准备可审阅结果。当前本机缺完整 Xcode 和 iOS 模拟器，不能把 Mac 上的触控事件模拟宣称为 iOS 实机通过。
