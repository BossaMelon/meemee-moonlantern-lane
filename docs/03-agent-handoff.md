## 3. 技术路线建议，不是已核验依赖合同

优先候选：TypeScript 的纯逻辑核心＋2D 浏览器呈现。对固定店面、数据化规则、自动交互与离线单机较合适。可选择 Phaser 等 2D 框架，也可用轻量 Canvas/DOM；本轮没有检查当前版本与 API，采用前须看实际运行时和官方文档并固定版本。

备选 Godot：适合更强场景与角色表现，但须先证明 agent 可以无编辑器手工操作地创建、运行、导出和测试。不要仅因为“做游戏就该用引擎”增加工具链。记录选择理由，选一条后保持稳定。

建议边界：

- `simulation`：库存、实例、交易、每日状态机、需求、升级、种子随机。无渲染依赖。
- `content`：商品、配方、客群、事件、七日流程，带唯一 ID 和静态校验。
- `presentation`：场景、界面、动画、输入与声音。
- `persistence`：有版本号的完整存档、至少一个可恢复快照、导出/导入。
- `verification`：种子回放、经济策略模拟、关键路径自动交互和截图。

日状态：预告→淘货→整备→营业→结算→保存。每个阶段转换定义能否返回和提交时点。交易使用唯一操作 ID 或等效防重方案；重复输入不应重复扣款/发货。NPC 视觉移动不决定经济正确性；渲染卡顿不能改变订单数或随机结果。

暂停时营业时钟停止。普通销售在固定 tick/离散事件中处理。存档包括阶段、阶段内时钟、待处理顾客/订单、库存实例、现金、随机状态、升级、已读事件；营业中退出恢复到相同状态或清楚标明的最近阶段快照，不允许重新抽货获利。

## 4. 分阶段实施与退出条件

### M0：可运行的经营骨架

交付一个可启动入口与一页运行说明；用占位图完成买货、上架、自动成交、结算、次日、保存/读取。首个原型不依赖美术生成服务或外部账号。

验收：一日可复算样例与设计文档一致；重复操作不复制物品；零资金可恢复；普通和特殊需求可区分。不需要完整动画或所有内容。

### M1：三日循环的趣味验证

交付六件左右商品、一件卖/用冲突奇物、两个有实质差异的升级、一个有预告需求事件、至少一位熟客。允许读设计修改不合理规则，但必须记录原因。

验收：两条策略产生不同经营行为；淘货确实影响营业；经营升级确实影响下一日；玩家能解释一笔好生意。安排真实试玩，若暂无人试玩，明确只通过功能验证，不声称好玩。

### M2：七日可玩切片

扩至设计文档的量级上限，补完整首日引导、两条路线、批量处理、自动化、夜市与短结局。此时才投入统一美术和音效。

验收：七日端到端通关、经营失败可恢复、不同路线可达章节目标、无强制长等待；大额资金和空库存等边界有可靠结果。保存退出再进入无重复奖励。

### M3：体验打磨与交付

修复试玩暴露的问题，优化操作和节奏，提供本地可玩构建与存档说明。部署是否需要另看实际使用方式和授权；本地作品不强制上线。

验收：在目标设备实际打开并试玩；标注功能证据、主观反馈与遗留问题。无需因每次改动重新跑无关检查。

## 5. 测试与平衡实验

必须覆盖库存守恒、成本与现金区分、价格取整/上限、预算与必需标签、实例装配/拆卸、重复结算、零资金恢复、随机与存档一致性。写针对失败路径的测试，不为文本和简单配置机械铺满测试。

实现后提供可重复的经济模拟入口（命令由实现者确定并写入 README，不伪造当前不存在的命令）。初始至少运行三个策略：保守周转、优先自用升级、事件备货；同一组种子横向比较。输出到达升级日、期末现金/库存、恢复次数、成交失败原因；不把自动策略的分数解释成人类快乐。

选择若干固定种子重跑七日，确保不会因基础材料缺货卡死；策略模拟如果都赢但只有一个最优套路，仍需检查决策差异。小样本目标是找软锁和明显支配策略，不证明全局平衡。

截图至少覆盖白天淘货、整备、营业、特殊需求、结算和窄窗口；图像生成成功不是视觉验收通过。实际检查文字遮挡、物品可辨认、交互目标大小和暂停反馈。

## 6. 纯 agent 制作的具体规则

内容用结构化数据；场景尽量代码生成；不要把关键流程藏在必须人工编辑的工具里。可视化测试需要真实跑应用，不能只检查构建通过。无运行时 LLM，所以没有 API 延迟/费用/联网作为玩家开店的前置条件。

先做可复现逻辑，再做少量风格样本，再扩素材。首版装饰采用插槽；NPC 少量状态机，不做全镇自由生活。故事是有限分支和事件表。记录素材清单与字体来源，不下载来路不明的整包资源。

## 7. 待验证与建议默认值

| 问题 | 暂定默认 | 如何验证 |
|---|---|---|
| 她更喜欢优化、收集还是人物 | 优化为主，收集和熟客辅助 | 三日试玩后的具体选择与理由 |
| 是否喜欢实时压力 | 默认可暂停，特殊对话暂停 | 观察营业负担，提供速度选项 |
| 平台与控制方式 | 桌面浏览器、鼠标优先、基础键盘 | 用户设备确认与实际打开 |
| 2D 表现和技术引擎 | 固定店面＋界面，不做大世界 | M0 能否稳定运行和自动验证 |
| 自用/售卖能否形成有效纠结 | 一件奇物、两种可行路径 | 两条策略都能过关且行为不同 |
| 七日是否够有趣 | 七日只是验证切片 | 第三日主动续玩、后四日出现新选择 |

不要为可逆实现选择反复索要批准；遇到材料范围、平台等问题可先推进独立工作。不可把主观未验证的“上瘾”承诺写成完成报告。

## 8. 交付与评审

实现非平凡候选时给一个独立 reviewer 实际 diff/快照、需求和验证证据；遵循适用用户约定的一次主评审预算，支持的问题修复后定向验证，不自动完整重审。开发产物、部署、实际运行和趣味验证分别报告。

本轮设计文档的独立检查记录另见 review-notes（如存在）；后续实现不因设计检查而免除代码要求。
